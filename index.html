How the "protection" works

A resource pack is a plain ZIP file. Protection tools can't encrypt it, because the game has to read it. Instead they exploit a gap. Minecraft reads only a small part of the ZIP and PNG structures and checks almost none of it, while archivers and image editors read and verify everything. The protector overwrites every field the game ignores with garbage. The game still loads the pack. Everything else sees a corrupted file.

No real data is lost or scrambled, so the damage can be repaired automatically. Each layer below shows the bytes it changes, why the game doesn't care, and how it's undone.

A ZIP stores everything twice

Each file inside a ZIP starts with a local file header (signature, name, sizes, CRC), followed by its compressed bytes and sometimes a small data descriptor. At the end of the archive, the central directory repeats the metadata of every file and points to its local header. The last record, end of central directory (EOCD), tells readers where the central directory is.

What Minecraft actually reads

Java Edition opens packs with Java's built-in java.util.zip.ZipFile, which:

  1. Finds the EOCD record at the end of the file.
  2. Reads each file's name, compression method, compressed size and offset from the central directory.
  3. Jumps to the local header, checks its 4-byte signature and uses its name and extra-field lengths to skip ahead. The name itself is never read.
  4. Inflates the data until the deflate stream ends. The CRC-32 is never verified, and the uncompressed size only sets the buffer size.

Textures are then decoded by stb_image (through LWJGL). stb_image reads each PNG chunk's CRC field and discards it, never checks the zlib Adler-32 checksum of the pixel data, and skips chunks it doesn't know. That's why a protected pack loads in the game without a single error, while every other tool mentioned below fails on it.

The layers, one by one

01

Fake file names in local headers

ZIP

The name in almost every local header is replaced with ../ followed by backslashes, padded to exactly the length of the real name. Because the length is unchanged, every offset in the archive stays valid.

central directory  assets/myshader/shaders/include/vertex_body.glsl  48 bytes
local header       ../\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\  48 bytes
Minecraft
Uses only the length (48) to skip to the data.
Everything else
Readers that walk the local headers see a pack full of files called ../\\\\…, which also looks like a path-traversal attack. Windows' built-in tar lists nothing but these names. Python's zipfile stops with File name in directory … and header … differ. Info-ZIP unzip prints mismatching "local" filename for every file.
Fix
Local headers are rewritten from the central directory, which holds the names the game uses.
02

Zeroed CRC-32 checksums

ZIP

Every file has CRC-32 00000000 in both headers. Flag bit 3 ("data descriptor") is set, so the local header is allowed to leave CRC and sizes empty. The real values sit in a 16-byte data descriptor after the compressed data, where the central directory never points.

local header      50 4B 03 04 14 00 08 08 08 00 F6 05 5A 5D 00 00 00 00 00 00 00 00 00 00 00 00 30 00 00 00
                                    flags                   CRC-32      packed size uncomp. size
data descriptor   50 4B 07 08 2E 13 E1 5F 7D 07 00 00 AF 1E 00 00
                              5FE1132E    1917 bytes  7855 bytes
central directory … CRC-32 00 00 00 00 …
Minecraft
ZipFile never verifies the CRC.
Everything else
Every file fails its integrity check: unzip reports bad CRC 5fe1132e (should be 00000000) for every file, and archivers mark the whole archive as damaged.
Fix
Each file is decompressed and its CRC computed. It always matches the hidden descriptor.
03

Fake uncompressed size: 1337

ZIP

Every central directory entry claims the file is exactly 1337 bytes once unpacked. The compressed size is left correct, because the game needs it.

central directory … packed 7D 07 00 00 (1917)   unpacked 39 05 00 00 (1337)   real: 7855
Minecraft
Uses it only as the initial buffer size, then reads until the deflate stream ends.
Everything else
Readers that trust the size stop after 1337 bytes. Python's zipfile, for example, cuts every file off there and then fails with Bad CRC-32. More forgiving tools such as Info-ZIP unzip ignore it, which is why it's only one layer of several.
Fix
The real size is measured while decompressing.
04

Bogus disk number: a fake split archive

ZIP

ZIP archives can be split into volumes (.z01, .z02, …). Each central directory entry records which volume its file starts on. In a protected pack, almost every entry says volume 14,597. That is 1337 (0x0539) written with its bytes swapped.

central directory … disk number start 05 39 = 0x3905 = 14597 (should be 00 00)
Minecraft
Ignores every multi-volume field.
Everything else
Archivers that support split archives think the file data lives on volume 14,598 of a set they don't have. They ask for the missing parts or refuse to extract.
Fix
Set to 0. The new archive is a single volume.
05

Zeroed timestamps

ZIP

The central directory dates are set to the DOS epoch (1980-01-01 00:00). An extra "UT" field adds a Unix timestamp of 0 (1970-01-01). This doesn't break anything. It mostly makes extracted files look odd and hides when the pack was built. The local headers still contain the real build time.

central directory … time 00 00 date 21 00 … extra 55 54 05 00 07 00 00 00 00
local header      … time F6 05 date 5A 5D
Minecraft
Doesn't read timestamps.
Fix
The date and time from the local header are copied back.

The next three layers are inside the textures. A PNG file is a signature followed by chunks. Each chunk is length · type · data · CRC-32. The pixels live in IDAT chunks as a zlib stream: a 2-byte header, deflate data, and an Adler-32 checksum of the unpacked pixels.

06

PNG chunk CRCs XOR-ed with a key

PNG

Every chunk CRC in every texture is XOR-ed with the same constant, 0xA5C3F17B. It's easiest to see on IEND, which is identical in every PNG in the world:

normal IEND    00 00 00 00 49 45 4E 44 AE 42 60 82
protected IEND 00 00 00 00 49 45 4E 44 0B 81 91 F9   AE426082 xor A5C3F17B = 0B8191F9
Minecraft
stb_image reads the CRC field and throws it away.
Everything else
libpng, which most image editors and viewers use, rejects a bad CRC in a critical chunk. ImageMagick stops at the first chunk with IHDR: CRC error.
Fix
Every chunk CRC is recalculated.
07

Broken Adler-32 inside the pixel data

PNG

Fixing the CRCs alone isn't enough. The Adler-32 checksum at the end of each image's zlib stream is XOR-ed with a second key, 0x5A6B7C8D. The compressed pixels are left alone.

Adler-32 stored FB BC BE 4C   real A1 D7 C2 C1   FBBCBE4C xor A1D7C2C1 = 5A6B7C8D
Minecraft
stb_image's built-in inflater never checks Adler-32.
Everything else
zlib, used by libpng, decodes every pixel and then fails with incorrect data check. The image stays unreadable even in tools that tolerate CRC errors.
Fix
The pixel data is decompressed and the real Adler-32 written back. The compressed bytes stay identical.
08

A private marker chunk

PNG

Each texture gets an extra 4-byte chunk named iaPR, holding IAP + version byte 01, just before IEND. Its own CRC is valid. The protector probably uses it to recognize images it has already processed. Case matters in chunk names: a lowercase first letter means ancillary (safe to skip), and a lowercase second letter means private. Every decoder is allowed to ignore it.

length 00 00 00 04  type 69 61 50 52 "iaPR"  data 49 41 50 01 "IAP" v1  crc 93 E2 2A 76
Minecraft
Skipped.
Everything else
Also skipped. It's harmless, but it marks the file as processed by the protector.
Fix
Removed, together with any other private ancillary chunk.

What the unlocker does

  1. Finds the central directory the same way Java does, including the offset math Java uses when junk is added in front of the archive.
  2. For every file, follows the local header's length fields to the data, decompresses it and computes the real CRC-32 and size. Streams are inflated to their real end, so wrong sizes don't matter.
  3. For every PNG, recalculates all chunk CRCs and the Adler-32, and drops private chunks and junk after IEND. The pixel data is not re-encoded.
  4. Writes a brand-new ZIP with consistent local headers, the real names, CRCs, sizes and timestamps, and no data descriptors, extra fields or volume numbers.

Files that needed no repair keep their original compressed bytes, so JSON, shaders and models come out byte-for-byte identical. Repaired PNGs are stored (PNG data is already compressed), which is why the output can be slightly smaller or larger than the input.

Other tricks it also handles

Some protectors use other tricks as well. Rebuilding the archive from the central directory fixes these too:

  • Fake encryption flag or compression method in local headers (makes WinRAR ask for a password). Java only reads these from the central directory.
  • Junk bytes in front of the archive without adjusted offsets. Java compensates automatically, many tools don't.
  • Duplicate entries. ZipFile.getEntry returns the last copy, so that's the one that's kept.
  • Names that can't be extracted on Windows: CON, aux.json, : * ? |, trailing dots, .., absolute paths, and file/folder clashes such as a file called assets. These are renamed (unsafe characters become _, clashes get a ~1 suffix), never resolved into real paths, so a decoy can't overwrite a real file.
  • Zip bombs and broken decoys. Entries that unpack to more than 512 MB or don't decompress at all are skipped and listed as warnings.
  • PNG tricks: junk after IEND, a zlib header claiming a too-small window, IDAT chunks interleaved with other chunks, and deflate streams only stb_image can read (recompressed).

What it doesn't touch

The unlocker repairs packaging, not content. Hashed or random file names (like textures/7f3a9c2e….png), minified JSON and stripped shaders aren't corruption. Those files are valid, just hard to read, so they're left exactly as they are.
